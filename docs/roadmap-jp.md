# 今後の拡張

[English](roadmap.md)

今後の拡張の予定です。以下の内容は 2026年11月時点で確認したものです。

## 実装済み

以前のロードマップにあった項目のうち、アプリに入ったものです（使い方は README を参照）。

- **向きの推定**（最初の版）：3D Scene の見出しの **Estimate Orientation** で、[Orient Anything](https://huggingface.co/spaces/Viglong/Orient-Anything) を使って各モデルを垂直軸まわりに回転させます（`services/orientation.ts`）。改善点は4番。
- **遠近を考慮した配置**：**Perspective** チェックボックスで、点群、PC Box、モデルをピンホールカメラから3次元に戻し、手前の物体が拡大されすぎないようにします。残っている仮定は5番。

## 1. 3D生成への Pixal3D の追加（Hugging Face Space）

[Pixal3D](https://huggingface.co/TencentARC/Pixal3D)（Tencent ARC、SIGGRAPH 2026、MIT ライセンス）は、PBR テクスチャ付きのメッシュ（GLB）を出力する画像-to-3D モデルです。

### このシステムに合う理由

多くの3D生成モデルは、形状を独自の座標空間で作るため、画像の画素と3Dモデルの対応があいまいになります。Pixal3D は **ピクセル整合生成** を採用しています。MoGe で推定したカメラの画角を使って画素を3Dに逆投影するため、**生成されたモデルの正面が入力画像と1対1で一致します**。

このシステムでは、補完画像の中の物体領域（tightBox2d）が PC Box に一致するように、モデルの拡大率と位置を決めています（論文の 3.5.3 節）。正面が入力画像と一致するモデルなら、この位置合わせがより正確になると期待できます。

### 実現方法

- 公式 Space [TencentARC/Pixal3D](https://huggingface.co/spaces/TencentARC/Pixal3D) が ZeroGPU で稼働しており、`preprocess`、`generate_3d`、`extract_glb_api` の API を公開しています。TRELLIS.2 と同じ構成なので、同じ方法で追加できます（手元の GPU は不要）。
- 実装時に確認すること：`generate_3d` のパラメータ、シーン内でのモデルの向き、tightBox2d との位置合わせ。

### 点群への当てはめ

Pixal3D を点群との位置合わせと組み合わせれば、位置・向き・大きさをまとめて決められる可能性があります。

1. **Pixal3D で初期の姿勢を得る**：モデルが入力画像のカメラの座標で生成されるなら、カメラに対する向きは最初から合っている。Orient Anything（4番）は不要になる。
2. **見える面を取り出す**：そのカメラから見えるモデルの面を取り出す。
3. **位置合わせ**：その面を、物体のマスク内の点群（深度マップから作るもの）に、拡大率を含めて当てはめる（ICP / Umeyama 法）。位置、大きさ、向きの微調整が一度に決まる。ICP は初期の向きが大きくずれていると失敗しやすいが、Pixal3D なら良い初期値が得られる。見えている面どうしを合わせるので、一部しか写っていない物体（3番）にも効く可能性がある。

最初に確認すること：

- 出力の GLB がカメラの座標のままか、大きさと位置が正規化されるか。
- 入力は元の写真ではなく、補完した切り出し画像である。切り出しの位置からカメラの変換は計算できるが、補完で生成AIが物体を描き直したり、中央に寄せたりする可能性がある。
- 点群の精度は、5番の仮定（画角、遠/近の比）に左右される。

## 2. ComfyUI によるローカルでの3D生成

3D生成の選択肢として、Hugging Face Spaces に加えて **ComfyUI（ローカル）** を追加します。多くの利用者は適した GPU を持っていないため、既定は Spaces のままとします。

### 目的

- **ZeroGPU の利用上限や Hugging Face トークンが不要**：利用者自身の GPU で生成するため、待ち時間も安定します。
- **再現性**：モデルとワークフローのバージョンを固定できるため、論文の再現実験に向いています。
- **プライバシー**：画像が利用者の PC の外に出ません。
- **モデルを足しやすい**：ワークフローのファイルを差し替えるだけで、モデルを切り替えられます。

### 候補のモデル

ComfyUI の公式ドキュメントで確認した内容です。

| モデル | ComfyUI での扱い | 出力 | このアプリとの相性 |
|---|---|---|---|
| Pixal3D | 本体のノードで動く。テンプレート「Pixal3D & TRELLIS.2: Image to Model」 | PBR テクスチャ付きメッシュ（GLB） | 良い（1 を参照） |
| TRELLIS.2 | 本体のノードで動く。上と同じテンプレートで `Boolean (Switch to Trellis2)` により切り替え | PBR テクスチャ付きメッシュ（GLB） | 良い |
| Hunyuan3D 2.0 / 2.1 | 本体のノードは **形状のみ（テクスチャなし）** | メッシュ（GLB） | テクスチャ付き GLB を返す Hunyuan3D-2.1 の Space の方が良い |
| TripoSplat | 本体のノードで動く | **ガウシアンスプラット**。オプションの `SplatToMesh` で GLB に変換可能 | 優先度は低い（下記） |

このアプリは、モデルを GLB のメッシュとして読み込みます。そして、メッシュのバウンディングボックスから PC Box に合わせた拡大率と奥行きのずれを計算し（論文の式(10)(11)）、シーンを glTF/GLB で書き出します。TripoSplat の主な出力であるガウシアンスプラットは、この仕組みに合いません。オプションのメッシュ変換で GLB にはできますが、変換したメッシュが、最初からメッシュを生成するモデル（Pixal3D、TRELLIS.2）を上回る可能性は低いと考えます。

### 設計の概要

- 設定：ComfyUI のアドレス（既定 `http://127.0.0.1:8188`）と、**API 形式**のワークフローファイル（ComfyUI から書き出したもの）。
- Pixal3D / TRELLIS.2 のワークフローをリポジトリに同梱する。
- 呼び出しの流れ（ComfyUI の HTTP API）：
  1. `POST /upload/image`：補完・背景除去済みの画像をアップロード
  2. `POST /prompt`：`LoadImage` ノードにアップロードしたファイル名を入れて、ワークフローを送信
  3. `GET /history/{prompt_id}`：処理が終わるまで状態を確認
  4. `GET /view?filename=…`：保存ノードが出力した GLB をダウンロード
- Pixal3D のワークフローには背景除去（BiRefNet）が含まれており、スイッチで省略できる。このアプリの入力は背景除去済みなので省略する。
- 配置の処理は今のものを使い回す。モデルの向きはワークフローごとに設定する。

### 制約

- **NVIDIA の GPU が必要**：VRAM の目安は、Hunyuan3D 2.0 で約 6〜12GB（形状のみ／形状＋テクスチャ）、TRELLIS.2 で約 24GB（第三者のガイドによる推奨値）。Pixal3D のページには記載がない。
- **モデルのダウンロード**：Pixal3D には、本体の拡散モデルに加えて、TRELLIS.2 の形状・テクスチャ用 VAE、DINOv3、MoGe、BiRefNet が必要。
- **ブラウザからの接続**：アプリがブラウザから呼び出せるように、ComfyUI を `--enable-cors-header` 付きで起動する必要がある。
- **保守**：ComfyUI の更新でノード名が変わると、ワークフローのファイルを直す必要がある。
- **テスト**：GPU のある環境が必要（CPU だけの環境では確認できない）。

## 3. 一部しか写っていない物体の配置

### 問題

写真に一部しか写っていない物体（サンプルでは、天板の手前の端しか写っていないテーブルと、画像の端に細く写っている椅子）が、3Dシーンで実際よりかなり小さく配置されます。

### 原因

1. 画像補完で生成AIが物体全体を描き直すため、写っていた部分を補完画像の中から特徴点マッチングで見つけられない（AKAZE で一致する特徴点がほとんどない）。
2. そのため、マッチングは物体全体の枠（tightBox2d）で代用される。
3. 結果として、物体全体の3Dモデルが、写真に写っていた小さな部分の枠に収まるように縮小される。

人物、花瓶、カップは、ほぼ全体が写っているため、正しく配置されます。

### 改善の方向

- **VLM に写っていた部分の位置を尋ねる**：マッチングに失敗したとき、切り出し画像と補完画像を画像認識モデル（Gemini / OpenAI）に渡し、補完画像の中で切り出し画像の内容にあたる枠を答えさせる。
- **補完前のキャンバスの配置を使う**：補完の前に、切り出し画像は大きな白いキャンバスの決まった位置に置かれる（`prepareImageForCompletion`）。生成AIがその配置を保てば、そこから位置を推定できる。ただし、生成AIは物体を中央に描き直すことが多いため、結果の検証が必要。
- **大きさの事前知識**：物体の種類ごとの一般的な大きさ（例：椅子の座面の高さ約 0.45m）を、シーン内の人物との比率に使い、拡大率の範囲を制限する。
- **シルエットの当てはめ**：推定したカメラから3Dモデルを描画し、そのシルエットが写真の見えている部分のマスクと一致するように、拡大率と位置を合わせる。
- **ピクセル整合の生成**：Pixal3D（1番目の項目）のように、モデルの正面が入力画像と一致する生成方法なら、写っていた部分の位置を特定しやすくなる可能性がある。

### 実装の方針

人がこうした物体を置くときは、物体の実際の大きさ（写真の人物との比較）、どこに立っているか（床の上）、どの部分が見えているか（画像の端の先に続いている）を手がかりにします。小さな枠に物体全体を収めるのではなく、同じ手がかりを使います。

1. **一部しか写っていないことを検出する**：切り出しの枠が画像の端に接している、または VLM が「画像の端で切れている／隠れている」と答えた場合です。検出と同じ構造化出力で、どの部分が見えているか（例：「テーブルの天板の手前の端」「椅子の背もたれの右端」）と、物体がどの方向に続いているかも答えさせます。
2. **拡大率を枠からではなく、大きさの事前知識から決める**：人物はほぼ全体が写っていて正しく配置されるので、その身長（約 1.7m）からシーンの縮尺が分かります。VLM に各物体の一般的な大きさ（例：テーブルの高さ約 0.75m、椅子の座面の高さ約 0.45m）を答えさせ、モデルをその大きさにします。
3. **奥行きは見えている部分から求める**：見えている部分のマスクの深度の中央値（論文の式(4)）は、そのまま使えます。
4. **床に接地させる**：人物の足元（または立っている物体の最下点）から床の高さを推定し、家具の底をその上に置きます。
5. **見えている部分で位置を合わせる**：拡大したモデルを、手順1の見えている部分が写真の見えている領域に投影されるように動かします。残りの部分は、画像の外や隠している物体の後ろに伸びます。
6. **シルエットで微調整する**（任意）：推定したカメラからモデルを描画し、画像内のシルエットが見えている部分のマスクと一致するように、位置と向きを調整します。

手順1〜5は新しいモデルが不要なので、まずサンプル写真で試せます。

## 4. 向きの推定の精度向上

最初の版は実装済みです（上の「実装済み」を参照）。写真での見え方と、モデルを正面から描画した画像の両方に Orient Anything を使い、視線方向の補正を加えています。改善の方法：

- **深度マップを使う**：人物の両肩など、左右に対になる点を2次元で検出し（MediaPipe などの姿勢推定）、深度マップからそれぞれの奥行きを読みます。奥行きの差から、Orient Anything とは独立に体の向きを計算できます。
- **画像認識モデル（VLM）に尋ねる**：切り出し画像を OpenAI / Gemini に渡し、どの方向を向いているかを構造化出力（例：15° 刻み）で答えさせます。結果の照合に使えます。
- **描画して比べる**：生成した3Dモデルを回転角を変えながら（例：10° ごと）描画し、シルエットや見た目が写真の切り出し（マスク）に最も近い角度を選びます。どの物体にも使えますが、計算量が多くなります。
- **Orient Anything V2**（[Space](https://huggingface.co/spaces/Viglong/Orient-Anything-V2)、ZeroGPU）は、2枚の画像の相対的な方位角と、物体の対称性（向きの数）も返します。2回の推定と確信度のしきい値を、これに置き換えられる可能性があります。
- **評価**：複数の写真で、手作業で合わせた角度と比べます。

## 5. カメラと深度の較正

遠近を考慮した配置（上の「実装済み」を参照）は、まだ2つの仮定に頼っています。

- **画角**：水平画角を 60° と仮定しています。EXIF から読むか、カメラの内部パラメータを推定するモデル（MoGe など）で求められます。
- **遠/近の距離の比**：Depth Anything V2 の相対的な視差は画像ごとに全範囲に引き伸ばされるので、比が分からず、Depth スライダーで設定しています（既定 1.5。サンプル写真で調整）。メトリック深度のモデル（Depth Anything V2 Metric、Depth Pro、MoGe など）を使えば実際の距離が得られます。シーン内の物体の一般的な大きさ（カップ、人物の頭など）から比を推定する方法もあります。

向きの推定の視線方向の補正も同じ画角を使っているので、こちらの精度も上がります。

## 6. 人物の顔の改善

### 問題

人物の3Dモデルの顔が不自然（不気味）に見えます。

### 原因

- 補完した全身の画像（1024×1536）の中で、顔は数十ピクセル分しかない。
- 汎用の画像から3Dを作るモデル（TRELLIS.2、Hunyuan3D-2.1）は、その大きさでは顔の凹凸（目のくぼみ、鼻、口）を作れず、のっぺりした形に目鼻を描いたような見た目になる。TRELLIS.2 はすでに上限に近い設定（解像度 1024、テクスチャ 2048）で動かしている。
- 人物は `type: 'person'` として見分けているが、補完や3D生成では物体と同じ扱いになっている。

### 改善の方向（試す順）

1. **人物向けの補完の指示**：`person` のときだけ、顔をはっきり自然に描くように指示する（正面寄り、目を開けて、表情は穏やか）。手軽だが、写真で顔がぼけていると描き直されるので、本人には似なくなる。
2. **TRELLIS.2 の解像度を 1536 にする**：形が少し細かくなる。生成時間と ZeroGPU の利用枠は増える。
3. **3D生成の前に顔を補正する**：顔補正のモデル（CodeFormer など）の Space で、補完した画像の顔をくっきりさせる。
4. **顔を作り込まない**：顔のテクスチャをぼかす、または肌の色で塗りつぶす（マネキン風）。不気味さはなくなり、シーン再構成にはこれで十分な可能性がある。
5. **人物専用の3D生成モデル**（PSHuman、LHM など、人体のモデルを使うもの）：品質は最も良いが、Space として使えるか、ライセンスはどうかの確認が必要。

**状況**：1（補完のオプション **Redraw faces**）と 2 は実装済み（Hunyuan3D-2.1 も Octree Resolution を 384 に）。それでも不気味さが残る場合は、次に 4 を選べるようにし、その後 3 か 5 を検討する。
